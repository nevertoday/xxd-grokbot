A problem report from a user is often a single line, like "I tapped it and nothing happened." Which page? Phone or computer? They didn't say. Whoever writes the code has to guess, then try one thing after another, and sometimes a whole afternoon goes by and they never see it. Maybe you built a small website yourself, maybe you pay someone to write the code, or maybe you're on a small team making an app. Either way, you've probably had reports like this.

By the end of this page, when a user reports a problem, your bot tries it first. It takes a test account (one made just for trying things, with no real customer's details in it), follows what the user described step by step until the problem shows up again, and brings back every step, the screenshots, and which browser it used. Someone writes "needs repro" in your team's bug channel in Slack, and it starts.

To reproduce a bug means to make it happen again, and you can only fix what you can see. Replying to the user is only one step in the process. What you want is for every problem to reach the person who writes the code with steps they can follow to see it. <mark>The steps it brings back should let someone else follow them and see the same bug.</mark>

## The goal is steps anyone can follow

The official docs call this Bug reproduction. See [Use cases](https://docs.x.ai/grok-bot/use-cases#bug-reproduction).

Make a new <Term k="bot" /> and call it Potato for now. Once it understands the job, it can rename itself (see [Lesson 2](/en/start/2-first-bot/)). Send it the goal:

<Copy id="br-goal" title="First message: the goal" code={`Hi Potato. When users report a problem it's always just "I tapped it and nothing happened," and the developers end up guessing for a whole afternoon. From now on, when a user reports something, you try it yourself first, write down exactly what to tap to make it happen, and then pass it on, so nobody has to guess. This one's yours now.`} />

## Tell it how you reproduce a bug

Next, tell it how your team reproduces a bug today. There's a lot to say here, so pressing `Cmd/Ctrl+D` and talking is quicker than typing. Two words in the example first. Staging is a copy of your website or app that's only for trying things, so breaking it doesn't affect real users. A ticket is the record of one problem, kept here in Linear, and your team talks tickets over in a feedback channel in Slack. Swap in your own environments and tools:

<Copy id="br-process" title="Second message: your process" code={`When a new ticket comes in, I read what the user wrote and look at their screenshot a couple of times, then check the feedback channel in case someone else hit the same thing. Then I open staging, make a fresh test account, and follow their steps one by one, taking a screenshot at each step and noting the browser and version. Just open staging in your own browser. The usual snag is a step the user left out, like they actually signed out and back in first, so I try every order I can think of. If it just won't happen, I write down every way I tried. I never touch a real customer's details, and I don't change a single setting on the live version. When I'm done, I follow my own steps once more, and if I can see the bug, it's ready to hand over. The developers tell me afterward whether the steps worked for them.

Don't go clicking around staging yet. First tell me how you'd reproduce one, and I'll tell you what's off.`} />

The example asks for the browser because the same button can work fine on a computer and do nothing in a phone's browser, and whoever writes the code needs to know where it broke.

It explains how it plans to go about it first. Correct whatever's off and go a few rounds, then let it start once it has it right. When it needs Linear or Slack, it shows a **Connect** card in the chat. Open it and sign in.

## Bring something back even when it won't reproduce

Reproducing a bug tends to get stuck in two places: you try and try and it won't happen, or what the user says doesn't match their screenshot. You know what to do then, but your bot needs to be told. And there are a few kinds of steps you don't want it clicking through on its own, even in staging. So give it your rules:

<Copy id="br-judge" title="Third message: how you decide" code={`There are a few situations I already know how to handle, and you should know them too. Even if it won't happen, don't come back empty-handed: say where you tried, which account you used, and every way you tried it. If what the user says and their screenshot don't match, write both down as they are. Don't pick one for them. Let the developers decide. If a step means paying, deleting something, or changing who can see or edit what, stop and ask me first, even in staging.

I'm sure I've left things out. Ask me first about whatever you'd be least sure of while reproducing, one question at a time. After that, let's walk through that bug from last time that only showed up on phones, start to finish.`} />

The first rule can look like wasted effort, but it really helps, because whoever writes the code sees right away which paths were already tried and doesn't repeat them. The last rule is there because staging can still touch real things, so those steps are your call. Swap that last line for a problem your team actually ran into, ideally one that went wrong at the time. Watch how it would handle it, and tell it on the spot where it goes off. Do these rounds in the chat, and don't set anything to run on its own yet. For a fuller way to ask, see [Have it find what you left out](/en/howto/prompts/#p-gaps) on the prompts page.

## When someone asks, it gets to work

Once it has reproduced a few bugs this way and its steps have worked, let it start on its own. Save the process as a <Term k="技能" /> first, then set up a <Term k="routine" />. This job doesn't start on a schedule. It waits for a line in Slack. When someone writes "needs repro" in the channel, it starts.

<Copy id="br-routine" title="Fourth message: let it start on its own" code={`Save the way we just worked out for reproducing bugs as a skill called "Bug repro." Then set up a routine: when someone posts a message in #bug-reports with a ticket link and "needs repro," open that ticket, use the skill to reproduce it in staging, and post the steps, screenshots, and browser details here in our chat. Don't post anything in Slack until I approve it.`} />

Keep the <Term k="触发条件" /> narrow, with one channel and one phrase. Watching every message is noisy and spends a lot of usage. One more thing. A Slack trigger needs Slack connected on the Cursor account that owns the bot. See [Slack triggers](https://docs.x.ai/grok-bot/skills-routines-and-automations#slack-triggers) in the official docs.

What it brings back looks something like this:

<Reply code={`Reproduced it, using a new test account. No real data touched.
1. Open staging in a phone browser and sign in
2. Tap "My orders," then the order at the top
3. Tap "Request refund": the button turns gray and nothing happens (screenshot 2)
The same steps in a computer browser open the refund page fine (screenshot 3), so it looks like a phone-only problem.
Browser and version are at the end. Want me to post this to #bug-reports?`} />

After the first few runs, follow its steps yourself and see whether the bug shows up. Check that the screenshots capture the moment it goes wrong. Then make sure it used a test account, touched no real data, and posted nothing in Slack.

To try it now, post a message with a ticket link and "needs repro" in that channel. To see what it stops to ask you about first, read [Approvals and privacy](/en/howto/approvals-privacy/).

## Stuck?

<Q q="It's asking for the test account password.">
Save it in <Term k="Vault" />, or enter it in a Secure Form when the bot shows one. Either way, the bot never sees the password. Never paste a password into the chat.
</Q>
<Q q="Someone wrote needs repro, and nothing happened.">
Check these three things:

- The message was posted after the routine was created.
- It's in the channel the routine watches, and it has the phrase.
- Slack is connected on the account that owns the bot.

Open the routine, and **When to run** spells out which channel and phrase it watches.
</Q>
<Q q="Staging won't load.">
Some sites drop connections from the bot's computer. You can open **Settings → Computer**, and under **Your computer** turn on **Route traffic through this computer**. But if staging is on your company's private network, this setting won't reach it. An admin has to install a networking client for the bot, and only the Enterprise plan offers that. See [Connect to private networks](https://docs.x.ai/grok-bot/private-networks) in the official docs.
</Q>
